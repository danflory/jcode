# SPR-0009: workflows-not-invocable-as-slash-commands

## Problem Statement

Gemini workflows, and the equivalent Overwatch `.agents/workflows/*.md` set, are
procedures that carry a name, a description, and a sequence of steps. jcode has
no way to invoke them as commands:

- They cannot be invoked as `/name args`.
- When mapped into jcode at all, they are surfaced **inconsistently** — often
  read as reference text rather than executed as a procedure, and never receive
  caller arguments.

The effect is that a user of jcode cannot say "run workflow X with these
arguments" the way they can with Gemini or Claude slash commands. Procedures
that are trivial to run in other clients are effectively dead on arrival in
jcode.

## Evidence (verified by reading the code)

1. **Skills are discovered ONLY as `<dir>/skills/<name>/SKILL.md`, and the
   frontmatter REQUIRES `name` + `description`; parse failures are warned and
   skipped.**
   - `SkillFrontmatter` declares `name: String` and `description: String` as
     required fields:
     `crates/jcode-base/src/skill.rs:26-34`.
   - `load_from_dir` iterates a source dir, and for each subdirectory only
     accepts a `SKILL.md` whose parsed frontmatter succeeds; nothing else is
     registered:
     `crates/jcode-base/src/skill.rs:468-479`.
   - `parse_skill` maps a parse error through a warning (the failure is logged
     and the skill skipped, not fatal):
     `crates/jcode-base/src/skill.rs:486-492`.

2. **The skill tool supports only `load|list|reload|reload_all|read`, and
   `args` are "accepted and ignored"** — this is the crux. A parameterized
   command cannot receive its parameter because the tool surface drops it:
   `crates/jcode-app-core/src/tool/skill.rs:31-45` (the `SkillInput` struct
   documents `args` as "currently accepted and ignored"; the `action` field is
   one of load/list/reload/reload_all/read).

3. **jcode has no workflow concept and no custom-command registry.** A search
   for `.agents/workflows` across `crates/` and `src/` returns zero matches
   (verified: `agentgrep` for `.agents/workflows` `glob=**/*.rs` → 0 files).
   Slash commands are built into the client; there is no user-extensible command
   table that could hold a workflow.

4. **Enforcement lives in a different subsystem: `[hooks] pre_tool`.**
   - `pre_tool` blocks a tool call on exit 2, with stderr shown to the model:
     `crates/jcode-base/src/config/default_file.rs:596-600`.
   - Hooks are **global-only** (no per-project hooks exist); all hooks except
     `pre_tool` are observers, and `pre_tool` is a gate:
     `crates/jcode-config-types/src/lib.rs:798-801`. There is no per-project
     enforcement slot, so per-project governance must route through a global
     dispatcher.

5. **`AGENTS.md` is instructions only.** It is loaded and appended to the prompt
   as reference text; it is never executed:
   - `crates/jcode-base/src/prompt.rs:458` (AGENTS.md loaded and pushed as a
     prompt part).
   - `crates/jcode-base/src/prompt.rs:595` (AGENTS.md static instructions per
     project).
6. **jcode's MCP client implements ONLY the `tools` primitive, and it is the
   only jcode-recognized mechanism that is simultaneously durable,
   parameterized, and actually executed.**
   - `tools/list` result: `crates/jcode-base/src/mcp/protocol.rs:142`.
   - `tools/call` params (name + arguments): `:148`.
   - `tools/call` result: `:155`.
7. **There is NO MCP `prompts` support and NO MCP `resources` support in
   jcode.** A regex search for `prompts/list | prompts/get | list_prompts |
   McpPrompt | resources/list` under `crates/` returns zero matches (verified:
   `agentgrep` → 0 files). Consequently MCP cannot supply a typed `/name`
   slash command either.
8. **Per-project MCP config resolution order is `.jcode/mcp.json`, then
   `.mcp.json`, then `.claude/mcp.json`, merging servers in override order;**
   project-local MCP tools are registered per working directory:
   `crates/jcode-base/src/mcp/protocol.rs:577-582`
   (`load_project_locals`, with `register_mcp_tools_for_dir` used per working
   dir).

## Scope

- **In scope:** design of a custom command surface for jcode; argument
  substitution; the enforceable vs advisory split; a generated, hash-pinned,
  governed-CI-preserving artifact; a global `pre_tool` dispatcher keyed on
  `JCODE_HOOK_CWD` for per-project governance given jcode has no per-project
  hooks; and the **security posture** of the MCP execution surface under an
  internal-only network topology (single trust domain, capability and read scope,
  provenance, measured containment state) in `09_Security_Model.md`.
- **Out of scope for the documentation phase:** any change to `crates/`, `src/`,
  `temp/`, `~/.jcode`, or any existing SPR. That constraint governed documents
  01-05 and has since been superseded by the implementation phase: a working
  stdio MCP server now exists at `temp/mcp/ow_createspr/` and is registered in
  `~/.jcode/mcp.json`, both recorded and verified in `06_MCP_Server_OW_tools_Steps.md`
  §8. No change was made to `crates/`, `src/`, or the Overwatch repo.

## Requested Fix

A **decision** (not a survey) choosing among four candidate approaches detailed
in `03_Options_and_Decisions.md`, plus the interface contract in
`04_Command_Surface_Contract.md` and the governance/enforcement model in
`05_Enforcement_and_Governance.md`:

- **A. Custom command surface** — load command files from `.jcode/commands/`,
  `.agents/commands/`, `.claude/commands/`, `.gemini/commands/` with argument
  substitution.
- **B. Extend skills into real commands** — plumb `args` through and add a
  workflow loader reusing existing skill discovery.
- **C. No new surface** — generated hash-pinned `SKILL.md` wrappers + a CLI the
  command delegates to, with `pre_tool` gating.
- **D. MCP tool surface** — expose each workflow as an MCP tool (real
  parameters, real execution, real result), registered per project via
  `.jcode/mcp.json`.

The recommendation (Option A, `04_Command_Surface_Contract.md`) loads command
files with argument substitution and adds no second source of truth: the
governed source stays `.agents/workflows/<name>.md` and any jcode-facing command
file is a generated, hash-pinned pointer verified by a regeneration drift check.
The options each satisfy different goals (user-typed invocation vs
model-invoked execution); `03_Options_and_Decisions.md` states which goal each
satisfies and why A is recommended.

## UNVERIFIED Items

- **RESOLVED (2026-09-18).** The Overwatch `.agents/workflows/*.md` frontmatter
  convention is no longer asserted from the task brief. A representative workflow was
  read: `.agents/workflows/createSPR2.md` declares `id: 49920`, `title`, `status:
  ACTIVE`, `authorized_by`, `description`, `implements`, `phase: DEVELOPMENT`, a
  `scope:` list of path/access pairs, `type: DOC`, and `version`. Two consequences that
  matter for this SPR: there is **no `name` field**, and the file is a flat `.md`, so it
  cannot satisfy jcode's `skills/<name>/SKILL.md` contract with required `name` +
  `description` (`01_Deficiency_Report.md` evidence; `03_Options_and_Decisions.md`
  Option B). The `scope:` block is also
  the workflow's own declared read/write surface, which is the natural input to the
  enforcement model in `05_Enforcement_and_Governance.md`.
- No live Gemini client was run to demonstrate the failure interactively; the
  "cannot be invoked as `/name args`" claim is grounded in code inspection
  (no command registry) rather than an interactive repro. V-1 is the manual
  counter-check that remains. The grounding was strengthened but not replaced by
  the implementation work: a stdio MCP server had to be registered and connected
  before any workflow step became callable (`06_MCP_Server_OW_tools_Steps.md` §8),
  which is consistent with there being no user-typed command surface.

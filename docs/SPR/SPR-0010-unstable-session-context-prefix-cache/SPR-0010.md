# SPR-0010: Unstable Session Context Prefix — Volatile Timestamp in the First Provider-Visible Message Defeats Prompt Cache Reuse Across Swarm Workers

## Problem Statement

Every session's **first provider-visible transcript item** is a session-context
snapshot whose *third line is a wall-clock timestamp*. Because prompt-prefix
caching (DeepInfra, Anthropic, OpenAI, and every other provider that bills a
discounted "cached input" class) matches on a **byte-identical request prefix**,
the timestamp guarantees that **no two sessions ever share more than 60 bytes of
common prefix**. All stable content that follows the timestamp — OS,
architecture, jcode version, hardware, working directory — is consequently
uncacheable on the first request of every session.

This is not a cosmetic ordering issue. Measured on real session history, the
observable consequence is that swarm workers re-pay the **full uncached input
rate** on context that is identical across every sibling worker in the same
swarm.

### Observed: common prefix across sibling workers is 60 characters

Measured directly from `~/.jcode/sessions/*.json` inside the project sandbox VM
(13 child/worker sessions, grouped by model, longest common prefix computed per
group):

| Model | Workers | Longest common prefix |
|---|---|---|
| `deepseek-ai/DeepSeek-V4.1-Flash` | 3 | **60 chars** |
| `deepseek-ai/DeepSeek-V4-Flash-0731` | 8 | **60 chars** |
| `deepseek-ai/DeepSeek-V4-Flash` | 2 | **60 chars** |

The common prefix terminates at the volatile field, mid-timestamp:

```
<system-reminder>\n# Session Context\nDate: 2026-09-18\nTime: 0
                                                            ^ divergence
```

Everything a sibling worker genuinely shares — the reminder wrapper, the
heading, `OS:`, `Architecture:`, `Jcode version:`, the hardware block, and (for
same-directory workers) `Working directory:` — sits *after* the divergence point
and is therefore priced as fresh input.

### Why this matters for swarms specifically

A swarm spawns many workers that each carry near-identical leading context. The
entire economic case for wide fan-out rests on those siblings hitting the cached
rate. The current layout forfeits that on every worker's first request, and the
loss scales with fan-out width.

## Expected Behavior

- The session-context snapshot's **stable** fields should form a contiguous
  block at the head of the first provider-visible message, with no volatile
  field interleaved.
- Any volatile field (wall-clock time in particular) should either be ordered
  **last**, or excluded from the provider-visible prefix while remaining
  available for display.
- Two sessions started on the same machine, same jcode build, and same
  working directory should share a common prefix covering the whole context
  block, not just the reminder wrapper and heading.

## Reproduction Steps

1. Start two sessions on the same machine with the same working directory.
2. Read each session's first `messages[]` entry and extract its text content.
3. Compute the longest common prefix of the two strings.
4. Observe it truncates mid-`Time:` line (60 characters), not at the end of the
   context block.

Programmatic form (run against any two sessions):

```bash
python3 - <<'EOF'
import json, os, glob
def first_text(p):
    d = json.load(open(p))
    c = d["messages"][0]["content"]
    if isinstance(c, list):
        return " ".join(x.get("text","") for x in c if isinstance(x, dict))
    return c or ""
ps = [f for f in glob.glob(os.path.expanduser("~/.jcode/sessions/*.json"))][:2]
a, b = map(first_text, ps)
n = 0
while n < min(len(a), len(b)) and a[n] == b[n]:
    n += 1
print("common prefix chars:", n)
print(repr(a[:n+10]))
EOF
```

## Impact

- **Cost.** Uncached input is billed at 3.3x the cached rate on the models in
  use (measured: `DeepSeek-V4-Flash-0731` $0.06 vs $0.015 per 1M;
  `DeepSeek-V4.1-Flash` $0.20 vs $0.006 per 1M). Every worker's first request
  pays the uncached rate on its entire context block rather than the cached one.
- **Fan-out economics.** The savings from aggressive swarm use are reduced
  precisely in proportion to how much of a worker's leading context is stable,
  which is most of it.
- **Model-choice distortion.** Because the cached-vs-uncached rate ratio differs
  sharply between model tiers, this defect biases which model appears cheaper
  for workers, and can invert the correct tier decision. See
  `03_Cost_Evidence.md` for the break-even analysis this affects.

## Root Cause

`crates/jcode-base/src/prompt.rs`, `build_session_context` (line 699):

```rust
pub fn build_session_context(working_dir: Option<&Path>) -> String {
    let mut lines = vec!["# Session Context".to_string()];

    lines.extend(session_datetime_lines());   // <-- volatile, and placed THIRD
    lines.push(format!("OS: {}", std::env::consts::OS));
    lines.push(format!("Architecture: {}", std::env::consts::ARCH));
    lines.push(format!("Jcode version: {} ({})", ...));
    ...
}
```

`session_datetime_lines` (line 726) emits, in order:

```rust
[
    format!("Date: {}", now.format("%Y-%m-%d")),
    format!("Time: {}", now.format("%H:%M:%S")),      // volatile to the second
    format!("Timezone: {}", now.format("%Z")),
]
```

`Time:` is at **position 3** of the block, ahead of every stable field.
`Date:` is also volatile, on a daily boundary.

The message is then injected as the **first** provider-visible transcript item
(`crates/jcode-base/src/session.rs:929`,
`ensure_initial_session_context_message`), whose doc comment states the intent
explicitly:

> Persist an immutable session-context snapshot as the first provider-visible
> transcript item for new sessions.

So the design correctly places a context block first, for prompt-cache benefit,
but populates it in an order that destroys the benefit. The immutability is
per-session; across sessions it is not stable, which is exactly the swarm case.

**Defect class.** Volatile field ordered ahead of stable fields inside a block
whose stated purpose is prefix stability.

## Scope

- **Affected component**: `crates/jcode-base/src/prompt.rs`
  (`build_session_context`, `session_datetime_lines`), affecting
  `crates/jcode-base/src/session.rs` (`ensure_initial_session_context_message`,
  `refresh_initial_session_context_message`).
- **Environment**: Version `v0.85.15-dev (572f2eb0d)`; branch `dev`;
  OS Linux (Ubuntu); shared server daemon with headed TUI clients; swarm with
  `swarm_model = "deepseek-ai/DeepSeek-V4-Flash-0731"` and coordinator
  `deepseek-ai/DeepSeek-V4.1-Flash`, both via DeepInfra.
- **Severity**: Major (cost correctness; no functional breakage).
- **Status**: Confirmed.

## Requested Fix

Reorder `build_session_context` so the stable block is contiguous and any
volatile field is last:

1. Keep `# Session Context` as the first line.
2. Emit **all stable fields** next, in a fixed order: `OS`, `Architecture`,
   `Jcode version`, hardware, `Working directory`, git info.
3. Emit volatile datetime fields **last**, or drop `Time:` from the
   provider-visible snapshot entirely (retaining it for display, since the
   message already carries `display_role: System`).

A secondary consideration recorded in the Deficiency Report: `Working
directory:` is itself a differentiator between workers in sibling clones or
worktrees. It is stable across same-directory workers and should remain, but its
position relative to other volatile fields should be considered.

### Follow-ups

- Decide whether `Time:` should be dropped from the snapshot or merely moved
  last. Moving it last recovers the whole stable block; dropping it additionally
  removes intra-day divergence.
- Decide whether `Date:` should remain provider-visible at all.
- Re-measure worker cache hit rate after the fix, using the role-split method in
  `03_Cost_Evidence.md`, to confirm the expected improvement.
- File the `model_cost_replay` `mix` accounting defect identified while
  gathering this evidence (it treats `input_tokens` as fully uncached, which
  understates true cache hit rates by roughly half). See `03_Cost_Evidence.md`.
